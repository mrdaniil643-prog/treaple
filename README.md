# МТ — музыкальный бар и караоке

Сайт с афишей, продажей входных билетов, заявками на бронь стола, меню кухни и кабинетом администратора.

## Запуск

Нужен Node.js 22.13 или новее. Внешних зависимостей нет: база — встроенный `node:sqlite`.

```bash
npm run dev        # разработка: демо-оплата, пароль админки печатается в консоль
npm test           # тесты бронирования и безопасности
npm run lint       # проверка синтаксиса JS
ADMIN_TOKEN=длинный-случайный-пароль npm start   # боевой режим
```

`npm start` включает боевой режим: без `ADMIN_TOKEN` длиной от 12 символов сервер не запустится, а демо-оплата выключена — бронирование закрыто, пока не подключён эквайринг (или явно не задан `DEMO_PAYMENTS=1`).

| Переменная | Зачем |
| --- | --- |
| `ADMIN_TOKEN` | Пароль админки, от 12 символов. Сгенерировать: `node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"` |
| `PORT` | Порт, по умолчанию 3000 |
| `DB_FILE` | Файл базы, по умолчанию `data/mt.db` |
| `VENUE_TZ` | Часовой пояс заведения, по умолчанию `Asia/Vladivostok` (Хабаровск, UTC+10) |
| `TRUST_PROXY` | Сколько прокси стоит перед сервером (за nginx — `1`). Без этого все гости за прокси считаются одним IP |
| `PUBLIC_ORIGIN` | Адрес сайта, например `https://mt-bar.ru` — нужен, если прокси подменяет заголовок Host |
| `DEMO_PAYMENTS=1` | Включить демо-оплату в боевом режиме (только для показа) |
| `QR_SECRET` | Ключ подписи живых QR. Если не задан, создаётся случайный и хранится в базе |
| `BACKUP_DIR` | Куда класть копии базы, по умолчанию `backups` рядом с базой. `off` — не делать копии |
| `BACKUP_KEEP` | Сколько дневных копий хранить, по умолчанию 14 |

### Для работы: свой сервер в России

Сайт собирает имена и телефоны покупателей, поэтому по 152-ФЗ (статья 18, часть 5) база должна лежать на сервере в России. Подойдёт любой VPS российского провайдера (Timeweb Cloud, Selectel, Yandex Cloud, REG.RU и другие) с 1 ГБ памяти и Docker.

1. Купите домен и направьте его A-запись на IP сервера.
2. На сервере: `git clone` этого репозитория, `cp .env.example .env` и заполните `.env` (домен, пароль админки, ключи ЮKassa).
3. `docker compose up -d`. Caddy сам получит сертификат HTTPS, сайт откроется по `https://ваш-домен`.
4. Обновление: `git pull && docker compose up -d --build`. База и её дневные копии хранятся в томе `mt-data`.

Этот адрес указывайте в ЮKassa при подключении магазина и в HTTP-уведомлениях (`https://ваш-домен/api/payments/yookassa`).

4. Обновление сайта: `cd mt && bash scripts/install.sh` ещё раз.

### Для показа: Render из GitHub

Серверы Render за рубежом, поэтому для настоящих продаж он не подходит (см. выше), но годится, чтобы показать сайт.

В репозитории лежат `Dockerfile` и `render.yaml`, поэтому Render сам соберёт и выложит сайт и будет обновлять его при каждом push.

1. Зарегистрируйтесь на [render.com](https://render.com) через GitHub и дайте доступ к репозиторию.
2. **New → Blueprint**, выберите репозиторий и ветку `claude/table-booking-ticket-system-7ax845`.
3. Render спросит `PUBLIC_ORIGIN` (адрес сайта, его видно после создания; можно заполнить позже) и `DEMO_PAYMENTS` (`1`, пока нет эквайринга, иначе онлайн-бронь закрыта).
4. Пароль админки Render создаст сам: **Environment → ADMIN_TOKEN**.

Тариф Starter платный (около 7 $ в месяц): на бесплатном нет диска, и база с заказами стиралась бы при каждом перезапуске. Свой домен подключается в **Settings → Custom Domains**, HTTPS Render выдаёт сам.

Тот же `Dockerfile` подойдёт для любого VPS: `docker build -t mt-bar . && docker run -d -p 80:3000 -v mt-data:/app/data -e ADMIN_TOKEN=... mt-bar`.

## Как устроены билеты

**Билет входной.** Место за столом он не закрепляет. У события есть вместимость (сколько билетов продавать, по умолчанию 136) и одна цена. В одном заказе до 10 билетов. Депозит в цену билета не входит: за стол действует депозит от 5000 ₽, его принимает бар (текст на сайте берёт `VENUE.tableDeposit` из `public/js/common.js`). Вместимость и цену админ меняет в блоке «Билеты»; вместимость нельзя сделать меньше уже проданного.

**Бронь стола — заявкой.** На странице события и на главной есть форма: имя, телефон, сколько гостей, пожелания, согласие на обработку данных. Заявка попадает в админку («Заявки на бронь стола»), администратор перезванивает и отмечает «Подтвердить» или «Отказать», может оставить заметку (например, номер стола). Денег за заявку не берут. С одного адреса не больше 10 заявок в час.

**Жизненный цикл заказа**

```
выбор числа билетов ──► held (билеты закреплены на 10 минут) ──► paid ──► refunded
                            │                                    (возврат гостем за 24 ч или админом)
                            └─► expired / cancelled (билеты возвращаются в продажу)
```

Билеты внутри заказа: `held` → `active` → `used` (прошёл на входе), либо `released` / `cancelled`.

**Защита от перепродажи.** Бронь проверяет, сколько билетов осталось, и создаёт билеты в одной транзакции. Каждый билет получает порядковый номер на событии, а уникальный индекс `(событие, номер)` среди живых билетов не даст выдать один номер дважды.

**Живой остаток.** Страница события подписана на изменения через Server-Sent Events: «Осталось N билетов» обновляется у всех, кто её смотрит.

**Отслеживание.**
- После оплаты заказ запоминается в браузере и доступен в «Мои билеты».
- С другого устройства заказ находится по номеру (`MT-XXXXXX`) и телефону.
- У каждого билета свой код и QR со ссылкой `/ticket?t=КОД`. Покупатель отправляет билеты друзьям и может подписать их именами гостей.
- На входе администратор сканирует QR камерой телефона (Chrome на Android) или вводит код. Повторный проход, билет на другое событие и возвращённый билет подсвечиваются.
- Каждое действие с билетом пишется в таблицу `ticket_log`.

## Вход гостей и контролёры

**Живой QR.** На билете QR и короткий код для входа меняются каждые 30 секунд: сервер подписывает номер для входа текущим 30-секундным интервалом (HMAC) и принимает подпись ещё один интервал. Скриншот перестаёт работать через минуту. Под QR идут часы и убывающая полоска — контролёр видит, что экран живой. Номер для входа отдельный от кода билета: по фото чужого QR нельзя ни открыть билет, ни получать новые QR. Постоянный код билета на экране не показывается. Если пропала связь, билет честно пишет «Нет связи».

**PDF-билет.** Кнопка «Скачать PDF» есть у каждого билета, а у заказа на несколько мест есть «Скачать все билеты в PDF» (по странице на билет). Файл собирается прямо в браузере. В PDF постоянный QR: его можно распечатать, и он пускает на вход один раз, как билет с Афиши. Защита от скриншотов остаётся у живого QR на телефоне. Для PDF действует простое правило: кто первым покажет QR, тот и пройдёт, поэтому файл не стоит выкладывать. После возврата QR из PDF перестаёт действовать.

**Правка из админки.** У оплаченного заказа есть кнопка «Изменить». В ней можно поменять:
- имя, телефон и почту покупателя;
- у каждого билета имя гостя, цену и статус: «Действует», «Прошёл» (так можно и снять отметку о проходе) или «Аннулирован» (билет возвращается в продажу; при оплате через ЮKassa деньги уходят на карту сами);
- номер для входа («Выдать новый QR»): старые живой QR и PDF перестают пускать. Это нужно, если PDF попал к чужим.

Сумма заказа пересчитывается сама, каждое изменение записывается в журнал. Открытый экран билета у гостя сразу показывает новое имя.

**Роль контролёра.** В админке в блоке «Контролёры» администратор создаёт приглашение с QR (одноразовое, действует 15 минут). Контролёр открывает его на своём телефоне — телефон получает защищённую cookie на 30 дней. Отключить телефон можно в админке или на самом телефоне. Контролёр не видит продажи, номера заказов и контакты гостей.

**Как проходит проверка**
1. Контролёр сканирует QR обычной камерой телефона. Ссылка `/c/<номер>.<подпись>` открывается в браузере, и билет гасится сразу. Удобнее встроенный сканер на странице `/staff`: там после каждого скана звучит сигнал и не копятся вкладки.
2. Результат на весь экран: зелёный «Проходите» с именем гостя, красный «Уже прошёл в 21:14», «QR устарел», «Билет не на сегодня», «Событие отменено».
3. У гостя билет тут же меняется на «Прошёл 21:14» со штампом.
4. Посторонний, отсканировавший QR, видит только «Это билет в МТ» — без кода и данных.
5. Если QR не читается, контролёр вводит короткий код для входа (6 символов, тоже меняется). Если у гостя сел телефон, администратор находит заказ по имени и нажимает «Впустить гостя».

Гашение атомарное: при двух одновременных сканах пройдёт один. Каждый проход пишется в журнал с тем, кто и как пропустил.

## Оплата

Оплата идёт через **ЮKassa** с «Чеками от ЮKassa»: чеки по 54-ФЗ уходят в налоговую и гостю сами, своя касса не нужна. Без ключей ЮKassa в режиме разработки оплата демонстрационная, а в боевом режиме онлайн-бронь закрыта.

**Как подключить**
1. В личном кабинете ЮKassa подключите «Чеки от ЮKassa» (раздел «Настройки → Чеки»).
2. «Интеграция → HTTP-уведомления»: адрес `https://ваш-сайт/api/payments/yookassa`, события `payment.succeeded` и `payment.canceled`.
3. «Интеграция → Ключи API»: скопируйте shopId и секретный ключ в настройки сервера (на Render: Environment):

| Переменная | Что это |
|---|---|
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Магазин и секретный ключ. Для проверки без денег возьмите тестовый магазин (ключ начинается с `test_`) |
| `PUBLIC_ORIGIN` | Адрес сайта: на него ЮKassa вернёт гостя после оплаты |
| `YOOKASSA_VAT_CODE` | Ставка НДС в чеке по справочнику ЮKassa: `1` без НДС (по умолчанию), `2` — 0%, `7` — 5%, `8` — 7%, `3` — 10%, `4` — 20% |
| `YOOKASSA_TAX_SYSTEM` | Система налогообложения: `1` ОСН, `2` УСН доходы, `3` УСН доходы минус расходы, `6` патент. Если в ЮKassa одна система, можно не задавать |
| `YOOKASSA_DEPOSIT_ADVANCE` | `0` (по умолчанию) — билет одной строкой: его продаёт организатор, а еду и напитки — бар. `1` — депозит отдельной строкой с признаком «аванс», только если билеты и бар на одном юрлице |

Ставку НДС, систему налогообложения и оформление депозита согласуйте с бухгалтером.

**Как проходит оплата**
- Гость вводит контакты и нажимает «Оплатить». Сервер создаёт платёж с чеком, где по строке на билет: «Входной билет: Отчётный концерт × Открытый микрофон, 25 октября». Бронь продлевается до 20 минут на время оплаты.
- Гость платит картой или через СБП на странице ЮKassa и возвращается в «Мои билеты». Страница ждёт подтверждения и показывает билеты.
- Заказ становится оплаченным только после того, как сервер сам запросил платёж у ЮKassa и сверил сумму. Уведомлению ЮKassa (у него нет подписи) одному не верим. Если уведомление потерялось, сервер сам проверяет незавершённые платежи раз в минуту.
- Если деньги пришли, когда бронь уже истекла, а билеты раскупили, деньги автоматически возвращаются вместе с чеком возврата.

**Возвраты** идут через ЮKassa с чеком возврата: гость сам за 24 часа до начала, администратор кнопкой «Возврат», а при аннулировании одного билета в «Изменить» возвращается только его цена. Сумма считается по цене, за которую билет оплатили, даже если цену потом поменяли. В админке у заказа видно «ЮKassa» и сколько уже возвращено.

Билеты продаёт организатор мероприятий (ИП), а бар «МТ» работает от ООО «Новый регион». Депозит входит в цену билета, бар принимает его в счёт заказа по договору с организатором: чек на блюда и напитки выдаёт бар.

## Безопасность

- **Доступ к заказу.** Управлять заказом можно только по секретному токену (144 бита), который получает покупатель, либо по номеру заказа вместе с телефоном. Токен передаётся во фрагменте адреса (`/tickets#order=…`), поэтому не попадает в логи сервера и прокси.
- **Ссылка на билет** показывает гостю только его билет: без номера заказа, контактов покупателя и кодов других билетов. Так один пересланный билет не даёт управлять всем заказом.
- **Коды.** Номер заказа — `MT-` и 8 символов, код билета — 12 символов; всё генерируется криптостойким `crypto.randomInt`.
- **Перебор.** Лимиты на IP для поиска заказа, брони, билетов и API. Вход в админку блокируется на 10 минут после 10 неверных паролей. Пароль сравнивается за постоянное время.
- **CSRF.** Изменяющие запросы принимаются только с собственного сайта (`Sec-Fetch-Site` / `Origin`) и только с `Content-Type: application/json`.
- **XSS.** Все пользовательские данные экранируются перед выводом. Content-Security-Policy запрещает сторонние и встроенные скрипты.
- **Заголовки.** `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: no-referrer`, COOP/CORP, HSTS за HTTPS.
- **Сервер.** Отдаются только файлы из `public/` с известными расширениями, без скрытых файлов. Лимит тела запроса 64 КБ, таймауты медленных соединений, ограничение числа открытых живых потоков.
- **Данные.** Весь SQL — подготовленные запросы. Текст от пользователей очищается от управляющих и невидимых символов, длина ограничена.

**Проверка.** В `.claude/skills/` установлены скиллы безопасности из [Claude-Code-CyberSecurity-Skill](https://github.com/Masriyan/Claude-Code-CyberSecurity-Skill) (MIT): `cyber-web-security`, `cyber-vulnerability-scanner`, `cyber-blue-team-defense`, `cyber-supply-chain-security`. Повторить проверку:

```bash
npm test                                                        # логика бронирования, QR, контролёры
npm run dev   # в другом окне, с ADMIN_TOKEN
ADMIN_TOKEN=... TARGET=http://localhost:3000 python3 scripts/security-check.py   # 70 атак по OWASP Top 10
python3 .claude/skills/cyber-web-security/scripts/owasp_scanner.py --url http://localhost:3000
python3 .claude/skills/cyber-supply-chain-security/scripts/supply_chain_auditor.py --project-dir .
```

Перед запуском в работу: поставьте сайт за HTTPS (nginx или Caddy), задайте `ADMIN_TOKEN`, `TRUST_PROXY=1` и `PUBLIC_ORIGIN`, копии `data/mt.db` сервер делает сам (см. ниже), но храните их и на другом диске: в базе заказы и контакты гостей.

## Что работает само

- **Брони.** Неоплаченная бронь снимается через 10 минут, билеты возвращаются в продажу.
- **Продажа.** Закрывается в момент начала события; прошедшие события уходят с афиши через 6 часов.
- **Вход.** QR и код для входа меняются каждые 30 секунд, погашенный билет у гостя сразу меняется на «Прошёл».
- **Копии базы.** При запуске и раз в сутки в `data/backups/mt-ГГГГ-ММ-ДД.db`, хранятся 14 последних. Восстановить: остановить сервер и положить копию на место `data/mt.db`.
- **Проверка живости.** `/api/health` отвечает, только если читается база; её опрашивают Docker и Render.
- **Выкладка.** На Render сайт обновляется сам после каждого обновления ветки (`autoDeploy`).
- **Проверки в GitHub Actions** при каждом push: синтаксис и ESLint, модульные тесты, запуск в боевом режиме, браузерные сценарии (`npm run e2e`: покупка, заявка на стол, вход по QR, PDF-билет, правка билета в админке, вёрстка на iPhone SE и 13), 77 проверок OWASP. Dependabot раз в неделю предлагает обновить закреплённые версии Actions.

Вручную пока: онлайн-оплата (нужен договор эквайринга, см. «Оплата»), заведение событий в админке, возвраты после 24 часов до начала, отправка билетов гостям (ссылкой, без почты и SMS).

## Поиск (SEO)

- **Значок в выдаче.** `/favicon.ico` (16, 32 и 48 px), `img/icon-120.png` для Яндекса, SVG для браузеров. Яндекс подхватывает значок не сразу, обычно за 1–2 недели после переобхода.
- **Заголовки и описания** с городом и адресом. У страницы события заголовок и описание собираются из названия, даты и цены.
- **Текст без JavaScript.** Сервер кладёт в страницу заголовок, дату, цену и меню до загрузки скриптов, поэтому робот видит содержание сразу.
- **Разметка schema.org.** На главной — бар с адресом, телефоном и часами работы и события афиши, на странице события — `Event` с датой, местом и ценой билета. По ней Яндекс и Google могут показать дату и цену прямо в выдаче.
- **Open Graph.** При отправке ссылки в Telegram, ВКонтакте и WhatsApp видна картинка (`img/og.jpg` или постер события), заголовок и описание.
- **`/robots.txt` и `/sitemap.xml`** собираются сами: в карте сайта главная, меню, документы и все текущие события; админка, билеты гостей и проверка QR закрыты от индексации.
- **Вебмастер.** Добавьте сайт в [Яндекс Вебмастер](https://webmaster.yandex.ru) и [Google Search Console](https://search.google.com/search-console), выберите подтверждение мета-тегом и впишите код в `.env` (`YANDEX_VERIFICATION=…`, `GOOGLE_VERIFICATION=…`), потом `bash scripts/install.sh`. В Вебмастере отправьте `https://<домен>/sitemap.xml`. Отдельно стоит добавить бар в Яндекс Бизнес (карточка на картах со ссылкой на сайт).

## Документы на сайте

В подвале каждой страницы есть реквизиты продавца и ссылки на документы: `/offer` (оферта), `/refund` (возврат), `/privacy` (политика обработки данных), `/consent` (согласие на обработку данных), `/contacts` (контакты и реквизиты). При оформлении покупатель отдельно отмечает согласие на обработку данных, без него сервер заказ не примет, время согласия сохраняется в заказе.

Реквизиты заданы в `public/js/seller.js` и продублированы в HTML документов, чтобы страницы читались без JavaScript. `test/legal.test.js` проверяет, что они совпадают. Шрифты лежат на сайте (`public/fonts`), сайт не обращается к сторонним серверам.
